# `Desmond@clearglassinc.com` activation runbook

## Status and decision

The mailbox is **not provisioned by this repository**. Creating it requires a paid mail-provider account plus authorized changes in the live DNS control plane. Those are human-controlled external actions; do not claim the address is operational until the acceptance checks below pass.

Use **Google Workspace Business Starter** as the initial host and create the primary user `Desmond@clearglassinc.com`. This is the smallest conventional setup for a single business mailbox and can later add aliases such as `hello@` without changing the website deployment. Email local parts are case-insensitive in normal delivery; use lowercase `desmond@clearglassinc.com` in DNS/provider configuration and the requested capitalization in display copy.

## Human-approved activation sequence

1. **Establish ownership and recovery**
   - Sign up at Google Workspace using `clearglassinc.com`.
   - Keep the existing personal address as the bootstrap/recovery address.
   - Enable MFA for the super-admin before changing MX records; create a separate emergency admin rather than using the daily mailbox as the sole recovery path.
   - Record the DNS host, registrar, billing owner, recovery owner, and rollback owner in the private password manager—not in Git.

2. **Verify the domain**
   - In Google Admin, copy the generated domain-verification TXT value.
   - Add that exact TXT record at the authoritative DNS provider and complete verification.
   - Never commit verification strings, recovery codes, passwords, or API tokens.

3. **Create the mailbox**
   - Create the user with local part `desmond` and a temporary unique password.
   - Require password change and MFA enrollment on first login.
   - Confirm the intended display name and recovery methods.

4. **Prepare authenticated delivery**
   - Replace any legacy/parking MX records with the MX value shown by the current Google Admin setup wizard. For current Google Workspace tenants this is normally `smtp.google.com` with priority `1`; the Admin console is authoritative for this tenant.
   - Publish exactly one SPF TXT policy at the root. If Google Workspace is the only sender, start with `v=spf1 include:_spf.google.com ~all`. Merge with an existing SPF record—never publish a second SPF policy.
   - Generate a 2048-bit DKIM key in Google Admin, publish the generated selector TXT record verbatim, verify DNS propagation, and then enable DKIM signing in Admin.
   - Start DMARC in observation mode: `_dmarc` TXT `v=DMARC1; p=none; rua=mailto:desmond@clearglassinc.com; adkim=s; aspf=s; pct=100`. Because aggregate reports can contain metadata about senders, restrict mailbox access and define retention. Move to `quarantine`, then `reject`, only after reviewing legitimate senders.

5. **Validate before publishing the address**

   ```bash
   python3 operations/email/verify_email_dns.py --dkim-selector google
   ```

   Substitute the selector generated by Google. A non-zero exit means activation is incomplete. Then:
   - Send from the new mailbox to an unrelated provider and reply back.
   - Inspect the received message headers for `spf=pass`, `dkim=pass`, and `dmarc=pass`.
   - Test password recovery and the emergency administrator.
   - Confirm the mailbox receives DMARC aggregate reports.
   - Only after all checks pass, replace the personal address on the public site in a separate reviewed change.

## Rollback and lockout recovery

- Before the MX cutover, export/screenshot the existing DNS records and their TTLs.
- If inbound mail fails, restore the prior MX set exactly; do not delete SPF/DKIM/DMARC evidence while diagnosing.
- If Google Admin access is lost, use the documented emergency administrator and registrar recovery process. DNS ownership alone is not a substitute for tested admin recovery.
- DNS caches respect TTLs, so rollback is not instantaneous. Keep the previous provider/account active during any future migration.

## Acceptance criteria

- The verifier reports PASS for MX, SPF, DKIM, and DMARC.
- External send and reply tests succeed, with SPF/DKIM/DMARC passing in headers.
- MFA and recovery are tested for the primary and emergency administrator.
- No credentials or provider verification secrets exist in Git.
- Public contact details are changed only after the mailbox is proven operational.
