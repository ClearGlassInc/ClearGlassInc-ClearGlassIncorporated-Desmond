## 2. Full remediation report

Ordered by severity. Each was fixed in its own commit on this branch.

### A1 — Lead form wrote prospects' personal data into the URL

- **Severity:** HIGH (privacy; live in production)
- **File:** `revenue-command.html` (added `0cfcfff`, 2026-09-21)
- **Problem:** Submitting the qualification form navigated to
  `revenue-command.html?full_name=…&work_email=…&primary_goal=…&current_challenge=…`
  and recorded nothing. The data landed in browser history, host access logs
  and `Referer` headers.
- **Root cause:** `API_BASE.replace(//$/,'')`. `//` opens a line comment, so
  the statement never closed and the whole script failed to parse
  (`SyntaxError: missing ) after argument list`). With no `submit` handler and
  no `method` on the form, the browser did a GET.
- **Fix applied:** Regex corrected to `/\/$/`. `method="post"` added to the form
  so any future script failure cannot put personal data in a URL.
- **Validation performed:** Chromium via Playwright, before and after, all
  required fields filled. Before: `pageerror` raised, URL contains
  `probe%40example.test` and the goal text. After: no `pageerror`, URL
  unchanged, the JS handler runs. Live exposure: Pages run #177 deployed
  `1d7de3c` at 2026-09-23T01:25Z, and that commit contains the defect. The
  live site itself could not be probed (§4).

### A2, A3 — Two pages rendered but nothing on them worked

### A9 — Node containers ran as root; no `.dockerignore`

- **Severity:** MEDIUM
- **Files:** `storefront/Dockerfile`, `admin/Dockerfile`, new
  `storefront/.dockerignore` and `admin/.dockerignore`
- **Problem:** `next start` ran as root. With no `.dockerignore`, `COPY . .`
  would send a local `node_modules` (host-platform `sharp`) and any
  `.env.local` into the image.
- **Root cause:** No `USER`. Docker does not read `.gitignore`.
- **Fix applied:** `USER node` with `--chown=node:node`, so `.next/cache`
  stays writable (admin uses `revalidatePath`). The ignore file excludes
  `node_modules`, `.next`, `.env*`. No env file is committed there, so no
  build input is lost. The control plane was already correct.
- **Validation performed:** **The Docker build was NOT executed** (no daemon
  here). Verified instead is the runtime model it produces: context filtered
  as `.dockerignore` filters it, owned by an unprivileged user, and as that
  user `npm ci`, `next build` and `next start` all succeed, `next-server`
  runs as that user, `GET /` returns 200 (storefront) and 307 (admin),
  `.next/cache` is writable, and there is no `EACCES`. Published images were
  never exposed: `release-supply-chain.yml` builds from a fresh CI checkout.
